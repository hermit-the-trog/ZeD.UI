# Performance: ZeD-GUI vs vanilla UI (Oct 22 2026)

Fullscreen 3840x2160, ZeD UI scale 1.75x, -debug on both runs, same Valley Station mall lot scene (geared character, trunk, duffel, parked cars, 8 passive zombies), zoom 1.0. Vanilla ran with ZeD off (dev-only shim mod ZeDQAShim) at vanilla's default UI sizes.

Machine: RTX 4090, i9-11900K, 64 GB, Windows 11, Java 25.0.1, game 42.21. Display 120 Hz. Frame cap from options.ini: frameRate=120, vsync on, uiRenderFPS=120.

## Results

Capped FPS is the average of two runs. Uncapped ms is the average of two runs with vsync off and the frame limit lifted in memory. "Extra" is ZeD minus vanilla, uncapped.

| Scenario | Capped FPS ZeD | Capped FPS vanilla | Uncapped ms ZeD | Uncapped ms vanilla | Extra ms |
|---|---|---|---|---|---|
| HUD only | 119.3 | 120.0 | 4.44 | 2.57 | +1.9 |
| Inventory + loot open | 76.0 | 120.0 | 13.11 | 4.66 | +8.4 |
| Item card / tooltip | 78.6 | 120.0 | 12.62 | 4.76 | +7.9 |
| Map open | 77.4 | 117.4 | 13.23 | 6.45 | +6.8 |
| Car at night, dashboard | 118.0 | 118.9 | 6.96 | 2.35 | +4.6 |
| Idle, nothing open | 119.4 | 120.0 | 4.58 | 2.64 | +1.9 |

- With any ZeD window open, the game runs at about 76 to 79 fps, against vanilla's 120 on the same machine.
- With windows closed and in the car, ZeD holds the 120 fps cap. Uncapped it still costs about 2 ms (HUD) and 4.6 ms (car) more per frame.
- Worst single frames: ZeD HUD 36 to 38 ms, vanilla 14 to 22 ms; ZeD car about 44 ms, vanilla 25 to 36 ms.
- Run-to-run noise: capped within about 4 fps; uncapped within 0.15 ms (0.28 ms on the ZeD map).

## Where the time goes

The cost is Lua drawing on the main thread, not the GPU.

Lua time per frame with both windows open (a wrapper timer around every prerender and render; use it to rank, not to subtract):

| Part | ms per frame |
|---|---|
| The belt (always on) | 2.63 |
| The two content panels (item lists) | 2.8 (4.2 with multi-container) |
| Four side rails (tab and container strips), about 0.3 each | 1.2 |
| Window frames | 0.8 |
| World window on Crafting | 1.1 |
| Maps panel | 0.5 |
| Vanilla's hotbar, for comparison | 0.12 |

Event handlers are not the problem: every handler, ZeD's and vanilla's together, totals about 0.5 ms per frame.

## Likely causes (leads from the code, not proof)

1. **The belt draws its round hands one pixel row at a time.** In ZeD_Belt.lua, disc() and ring() issue one drawRect per pixel row with a square root per row: about 500 draw calls per frame for the two hands at 1.75x. Its _layout() also rebuilds the box tables, strap runs and a signature string every frame. Fix: a pre-made circle texture per size, and cache the layout until the slots change.
2. **The windows' lists and side rails are rebuilt every frame.** InventoryRenderer.renderItemList recreates its layout constants and 8 closures every frame and redraws every visible row; the tab and container strips re-measure, re-stencil and redraw each frame. Fix: build the row model and strip layout only when the contents change, and reuse it.
3. **The dashboard is built every frame from many small tinted parts,** each looking up the light map. Fix: cache the lit composition per light level step and redraw only the moving parts.

## Caveats

- -debug on both runs makes both somewhat slower than a normal launch.
- Zombies passive and god mode: a fight would cost more on both sides.
- The scenes match closely, not exactly (the wagon settled about half a tile differently).
- The engine's hide-all-UI switch does not stop an element's own drawing code, so a true "no UI" floor was not measured.
- The inventory scene had two Character-window columns (the chest rig's column did not open).
- Above 120 fps the UI refresh stays capped at 120, which flatters whichever side draws more UI.
- Two 30 s runs per cell.

| Item card / tooltip | 78.6 | 101.4 | 120.0 | 12.62 | 9.56 | 4.76 | +7.9 | +4.8 |

- With the windows open the game now runs at about 98 to 102 fps (it was 76 to 79). The windows still cost about 5 ms a frame more than vanilla's.
- The HUD and the car are now within 1.4 ms of vanilla uncapped, and both hold the 120 cap.
- The belt alone: 2.63 ms a frame before, 0.72 ms after. The dashboard's own drawing: about 3 ms before, 2.2 ms after (with a timer on every part, so both high).
- Draw calls a frame (every ZeD draw counted in game): HUD 602 to 116, both windows 1430 to 904, item card 1354 to 827, map 1352 to 825, car at night 449 to 339.

### What changed

Nothing is drawn differently: every change keeps the same pixels, or is the same calls made faster.

- The belt (ZeD_Belt.lua). The round hands, their outlines and the focus wash were one rectangle per pixel row (about 500 a frame). They are now one picture each, the same pixels exactly: white masks baked at every size the scales 0.7 to 2.35 can ask for, Large text included (42/media/textures/ZeD/belt/round/, 285 small pictures, made by ZeDUI/tools/physpx/d_rounds.py with the Lua's own arithmetic), drawn tinted at 1:1 with drawTextureScaledAspect. A size outside that range draws the rows, equal rows merged. The layout (boxes, strap runs, closure) is kept until the token table, the character, the slots, the worn watch or the slot materials (looked up every second, as before) change. Key names, slot names and hand names are kept per language and test language; the profession buckle's id per profession.
- Every ZeD class draws through lean copies of drawRect, drawRectBorder, drawText, drawTextureScaled and drawTextureScaledAspect (Overrides/TextScale.lua): the same Java calls with the same values, without ISUIElement's longer path. Measured in game: a rect 1.56 us through ISUIElement against 0.60 direct, a text 3.12 against 1.02, a fitted texture 3.40 against 0.48 (raw/drawcall_micro.txt). A class with its own method keeps it (the action bar's fade).
- Text measuring (Scale.lua, ZeD.TM): widths and heights are kept per font and string, and dropped on a new token table, root scale, language, font-size option or resolution; nothing is kept while the fonts load. The zoom per font is kept the same way. ZeD.Atoms.truncateText keeps its answers on top of that. ZeD.tr keeps phrases with up to two text arguments per language and test language (Tr.lua).
- The lists (InventoryRenderer.lua): the category of each row comes from the list model (built when the container changes, as before) instead of a Java call per row per frame; the container key for List | Grid is kept per container (a car part's is still asked every frame); the belt tag test no longer builds a closure per row. ContainerControls.lua compares the containers and their sizes instead of building a string of them every frame. The Character window's title icons are looked up once.
- The tab strips (ZeD_TabPx.lua): each icon's six pictures are looked up once instead of building six file names per tab per frame; the five tones are worked out again only when the accent colours change (compared by value, since a window with its own accent swaps them in).
- The dashboard (ZeD_PixelParts.lua, ZeD_Plate.lua, ZeD_Dashboard.lua, ZeD_RadioOps.lua): a pixel-font text is kept as its rects, with runs that sit under the same run merged into taller rects (one cover per pixel, so the same picture); plate rect lists (lamps, halos, gear letters) are merged the same way once; a needle's pixels are kept per angle, and a moving needle reuses them while every sample lands on the same pixel; a lit needle's colours are kept per light state; the night speed ribbon draws runs of cells in the same light as one stretch. The design and badge lines are worked out once per car and language. The car and radio readings call their getters without making a closure each time. The light sampling was already four times a second and stays.

### How the pictures were checked

The stage scene is not the same twice (the car's random loot, radio presets and fuel, the items' random icon variants), so before and after were taken in the same game: perf_capture.lua shot 21 scenes with the new code (belt, both windows with multi-column lists, item card, Maps tab, dash by day and at night, at 1.75x, 2x and 1x; and the pair in light / blue, hicon / teal and dark / orange at 1.75x), then perf_hotold.lua loaded the files as they were before over the running game and the same 21 were taken again, on an opaque backdrop so the world behind the UI does not count. The image diff (raw/capture_ab_diff.txt): 5 of the 21 identical, and the other 16 differ only in the mini watch's minutes on the belt, the dash's fuel and temperature needles (still settling), and scattered pixels inside the map itself (the game's map renderer, not ZeD's drawing).

### Where the windows' time goes now
