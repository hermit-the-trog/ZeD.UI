# Performance: ZeD-GUI vs vanilla UI (Oct 22 2026)

Fullscreen 3840x2160, ZeD UI scale 1.75x, -debug on both runs, same Valley Station mall lot scene (geared character, trunk, duffel, parked cars, 8 passive zombies), zoom 1.0. Vanilla ran with ZeD off (dev-only shim mod ZeDQAShim) at vanilla's default UI sizes.

Machine: RTX 4090, i9-11900K, 64 GB, Windows 11, Java 25.0.1, game 42.21. Display 120 Hz. Frame cap from options.ini: frameRate=120, vsync on, uiRenderFPS=120.

## Results

Capped FPS is the average of two runs. Uncapped ms is the average of two runs with vsync off and the frame limit lifted in memory. "Extra" is ZeD minus vanilla, uncapped.

| Scenario | Capped FPS ZeD | Capped FPS vanilla | Uncapped ms ZeD | Uncapped ms vanilla | Extra ms |
|---|---|---|---|---|---|
| HUD only | 119.3 | 120.0 | 4.44 | 2.57 | +1.9 |
| Inventory + loot open | 76.0 | 120.0 | 13.11 | 4.66 | +8.4 |
| Item card / tooltip | 78.6 | 120.0 | 12.62 | 4.76 | +7.9 |
| Map open | 77.4 | 117.4 | 13.23 | 6.45 | +6.8 |
| Car at night, dashboard | 118.0 | 118.9 | 6.96 | 2.35 | +4.6 |
| Idle, nothing open | 119.4 | 120.0 | 4.58 | 2.64 | +1.9 |

- With any ZeD window open, the game runs at about 76 to 79 fps, against vanilla's 120 on the same machine.
- With windows closed and in the car, ZeD holds the 120 fps cap. Uncapped it still costs about 2 ms (HUD) and 4.6 ms (car) more per frame.
- Worst single frames: ZeD HUD 36 to 38 ms, vanilla 14 to 22 ms; ZeD car about 44 ms, vanilla 25 to 36 ms.
- Run-to-run noise: capped within about 4 fps; uncapped within 0.15 ms (0.28 ms on the ZeD map).

## Where the time goes

The cost is Lua drawing on the main thread, not the GPU.

Lua time per frame with both windows open (a wrapper timer around every prerender and render; use it to rank, not to subtract):

| Part | ms per frame |
|---|---|
| The belt (always on) | 2.63 |
| The two content panels (item lists) | 2.8 (4.2 with multi-container) |
| Four side rails (tab and container strips), about 0.3 each | 1.2 |
| Window frames | 0.8 |
| World window on Crafting | 1.1 |
| Maps panel | 0.5 |
| Vanilla's hotbar, for comparison | 0.12 |

Event handlers are not the problem: every handler, ZeD's and vanilla's together, totals about 0.5 ms per frame.

## Likely causes (leads from the code, not proof)

1. **The belt draws its round hands one pixel row at a time.** In ZeD_Belt.lua, disc() and ring() issue one drawRect per pixel row with a square root per row: about 500 draw calls per frame for the two hands at 1.75x. Its _layout() also rebuilds the box tables, strap runs and a signature string every frame. Fix: a pre-made circle texture per size, and cache the layout until the slots change.
2. **The windows' lists and side rails are rebuilt every frame.** InventoryRenderer.renderItemList recreates its layout constants and 8 closures every frame and redraws every visible row; the tab and container strips re-measure, re-stencil and redraw each frame. Fix: build the row model and strip layout only when the contents change, and reuse it.
3. **The dashboard is built every frame from many small tinted parts,** each looking up the light map. Fix: cache the lit composition per light level step and redraw only the moving parts.

## Caveats

- -debug on both runs makes both somewhat slower than a normal launch.
- Zombies passive and god mode: a fight would cost more on both sides.
- The scenes match closely, not exactly (the wagon settled about half a tile differently).
- The engine's hide-all-UI switch does not stop an element's own drawing code, so a true "no UI" floor was not measured.
- The inventory scene had two Character-window columns (the chest rig's column did not open).
- Above 120 fps the UI refresh stays capped at 120, which flatters whichever side draws more UI.
- Two 30 s runs per cell.
