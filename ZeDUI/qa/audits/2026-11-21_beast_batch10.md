# Beast day, batch 10 (Nov 21 2026, QA): what the retaken pictures' captions showed

Eight oddities from zooming into the retaken 4K pictures (Screenshots/beast_day_report/), each traced in the code by one
agent and attacked by a second (workflow wf_d4cf70be-4b6, crops in the session scratchpad verify10/). Five are real
bugs, below. Three are by design and are not sent: the amber square before "Surface" on every surface recipe is the
spec's static requirement chip (CRAFTING_SPEC.md:164-171; it goes to the KISS audit as a possible false alarm), the
rolled-up Character bar's "S..." is the title giving way to the stats with no room left (Organisms.lua fitStats), and a
book's list row can read 1% under its card for up to a second (ReadMarks CACHE_MS, said in its own header).

### B10-1 Reset to defaults skips Style: a Lite player stays in Lite and the button grays out (regression from beta 20)

- What the player meets: in Lite, ZeD setup, Reset to defaults: every extra goes back to Vanilla and off, UI scale to
  Auto, but Style still reads Lite with no changed mark, and Reset to defaults grays out as if nothing were left. With
  the rest already at defaults the button is gray as soon as the page opens, so Defaults can never take a Lite player
  back to Full, the setup ZeD starts on. The Style row also has no help line (LookStyleTip is shown nowhere) and no
  "Default: Full". Picture: B3-1_lite_after_defaults_extras_off.png (QA's script printed "Style reads Full" as fixed
  text without reading the control; fixed on QA's side below).
- Cause: ZeD records each option's starting item only for ids in Settings.lua's nameKeys table (792-822, the loop at
  823-831). Style came on Nov 18 (058a5ad9d, Lite step 1) without a line there, so it has no zedNameKey, no zedDefault,
  no tip key; buildSetup copies nil (ZeD_MainMenuOptionGroups.lua:457-463) and zedDefaults / zedOffDefault skip it
  (ZeD_MainMenuOptions.lua:1992, :2002; the button grays at :2069). Before that the eight Simple switches were rows with
  nameKeys entries, so Defaults put the full forms back. mapLight and restock have the same gap (mapLight breaks the
  promise in G.SETUP_HIDDEN's own comment, ZeD_MainMenuOptionGroups.lua:218-221).
- Fix: in nameKeys add lookStyle = "UI_ZeD_Settings_LookStyle", mapLight = "UI_ZeD_Settings_MapLight", restock =
  "UI_ZeD_Settings_Restock" (all keys exist in UI.json). zedDefault for Style is then 1 (Full: carryStyle runs later, on
  OnMainMenuEnter). Style is the page's first row (:174), so its onChange(1) puts back any picks kept from before Lite
  (B6-4) before the addition rows are reset; lite() reads the stored value, so the page keeps its Lite layout until
  Apply. Optional hardening: at ZeD_MainMenuOptionGroups.lua:463 fall back on ZeD.ModOptionsOwners.default("ZeD_UI",
  opt.id) as add-on rows do at :427, so a future option left out of nameKeys still resets.
- Behaviour note: after this, Defaults in Lite switches the player to Full (as Defaults switched Simple pieces back to
  Full before beta 21). Nothing in the docs or the director's Lite decisions exempts Style; if you think the director
  should pick, ask (one asker).
- QA after the fix: rt_system's Defaults check fails any of ZeD's own combo rows with no zedDefault (add-on combos may
  lack one by design); bxr_lite prints the Style row's live pick and gates the shot on Full.

### B10-2 The Craft card's Outputs always read 1, and name the first possible result

- What the player meets: Divide Food into 4 Bowls lists "Bowl of Pasta 1" and "Cooking Pot 1", each with a green square
  and the returned arrow; the recipe makes 4 bowls and gives the pot back. The 1 is wrong on every recipe that makes
  more than one: 159 of the game's recipes (Open Candy Package makes 5 and 5, both read 1). In 36 the single output is
  named in the title (Break Large Stone into Stones, 10; Make Coke, 4) and ZeD hides the Outputs section, so the amount
  shows nowhere. Picture: B6-16_alternatives_1_of_4.png (card foot).
- Cause: CC.prebakeOutputs (CraftingCore.lua:864-891) keeps a name and types but no amount; renderCraftCard sets have = 1,
  need = 1, isKeep = true on every output row (3068-3077), placeholder numbers from the first commit (506e75bae); isKeep
  prints the have count alone with a green square and the arrow (Molecules.lua:3869-3870, :3927, :3930-3937). The name is
  getPossibleResultItems():get(0) (CraftingCore.lua:98-105), the mapper's first entry. The spec asks for a yield
  (docs/specs/CRAFTING_SPEC.md:197-204; mockup zed-crafting-unified-v1.html:664 draws "x<yield>", no square or arrow).
- Fix: in prebakeOutputs keep the amount as vanilla reads it: local amount = 1; pcall(function() if
  output:getResourceType() == ResourceType.Item then amount = math.max(1, output:getIntAmount()) end end) (vanilla
  ISWidgetOutput.lua:147-151); renderCraftCard have = need = outDef.amount or 1; outputsRepeatTitle (895-907) hides the
  section only when that one output's amount is 1. Decide on purpose whether the yield is one craft's (vanilla) or
  times the batch (the mockup). One fix covers Craft, Build and the Journal (BuildingTab.lua:104, JournalTab.lua:584).
  The name: with food to divide in reach vanilla names the mapper's result for the slotted items (manual select,
  ISWidgetOutput.lua:286-295); to match, ask output:getOutputMapper() for the result of what is in reach (note
  ObjectCardPreview.lua:181-215's carried-item pick never runs: getPossibleResultItems already returns the mapper's
  results, so its #types == 0 gate never opens). Latent, harmless today: prebakeOutputs' validTypes stay empty because
  it calls getFullType (877) where script Items have getFullName.

### B10-3 A frozen food's item card never says Frozen

- What the player meets: a frozen steak's row reads "Steak (Fresh, Uncooked, Frozen)" (the game's own name) and its
  balloon has a Frozen tag, but its item card shows Cooked Raw and Fresh Fresh and nothing about freezing, while its
  Boredom +30 and Happiness -30 are entirely the game's frozen penalty. Frozen food does not cook until thawed and keeps
  the penalty until fully thawed; nothing on ZeD's card says so. With the card open the balloon is hidden ("the card
  says all of it already", ZeD_InvTip.lua:176-177), and a narrow list cuts the end of the row's name, where Frozen sits.
  Picture: B5-9_freezer_steak.png.
- Cause: NutritionFacts' state group holds only Cooked and Fresh/Rotten (ItemFactsPanel.lua:233-253); the title is
  getDisplayName (ItemCardOrganism.lua:1384, the bare name); the old card's Frozen badge (ItemCard.lua:63) stopped
  drawing in S121 (b433747e1). No ZeD file reads getFreezingTime.
- Fix: one row after Fresh (ItemFactsPanel.lua:247-251): label getText("Tooltip_food_Frozen") when isFrozen(), else
  getText("IGUI_invpanel_FreezingTime") when getFreezingTime() > 0; value the percent only while 0 < freezing time <
  100 (vanilla's tooltip shows its Freezing bar only then; at 100 plain "Frozen" is enough); valueClass "warn" only when
  isFrozen() and not Icecream or ItemTag.GOOD_FROZEN (the penalties apply only with the frozen flag). The model rebuilds
  every 250 ms (ItemCardOrganism.lua:634), no new probe. While there: stale food (neither fresh nor rotten) gets no
  freshness row; the loot card already says Stale (ZeD_LootCard.lua:78-82, copy its guard at :80).

### B10-4 The recipe list loses the open recipe when anything changes (Craftable sort)

- What the player meets: open a recipe's card, then bring what it lacks (planks dropped beside you, a crate in reach): as
  soon as any recipe turns ready or missing the list re-sorts, the open recipe leaves its alphabetical place for the end
  of the missing-and-station block, and once ready jumps to the top block. The list keeps its scroll, so the highlighted
  row is gone from view. Closing the card re-sorts too. Pictures: W25_floor_2_of_4.png, W25_floor_and_crate_4_of_4.png
  (the mold's row out of view in both, the scroll thumb unmoved).
- Cause: the Craftable key is pin * 10000 + rank * 1000 + missingCount * 10 (CraftingCore.lua:1152-1156), but only the
  open recipe ever has a count: CC.refreshRow zeroes every row once a second (:590) and CC.gatherDetail writes it back
  for the open one in the same frame, before the sort (:1340; CraftingTab.lua:564-596). Its key (2010+) sorts after
  every other missing or station row (all 2000, :82). Re-sorts come from any status flip in the 1.2 s scan (:407,
  :514-532) and from closeCraft (:1505-1512); refilter has no scroll handling (:1518-1528), the scroll is a kept fraction
  (:2200-2227), and the only follow is the controller's, on a change of focused id (:3272-3326). The code's own comment
  says moving the selected recipe is unwanted (:3496-3501).
- Fix: (1) drop the missing-count term: sk = pin * 10000 + st * 1000 (also stops the jump on close). (2) Keep the open
  recipe where it was on screen across a re-sort: before refiltering, take the row's offset from the view's top from
  last frame's zones (CC.render's local lastZones, :3125, since state.zones is reset at :3164 before refilter at :3167;
  state._listGeo is still last frame's) or from the old filteredCache; after, find its new content y as the row loop
  does and set state.scroll so it sits at the same offset, clamped (the controller follow at :3301-3320 uses the same
  arithmetic). Shared core: Build and the Journal get both.

### B10-5 The tucked-away inventory's tab counts worn things, the list does not ("Inventory 26" vs "8 items")

- What the player meets: with the inventory side rolled under its tab, the tab reads "Inventory  26" and its help line
  "26 items"; rolled down, the heading says "8 items" over 8 rows. The 18 are what he wears and his three bags (the
  list leaves them out; the Equip tab shows them). Pictures: B6-17_a_side_hidden_bar_current.png,
  B6-17_b_side_down_same_numbers.png.
- Cause: the tab's chip returns inv:getItems():size() (ZeD_CharacterWindow.lua:6950; WindowCurtain.lua:97-109, 186-190);
  the heading uses InventoryRenderer.shownCount (ZeD_CharacterWindow.lua:6503), which skips hidden, worn, held and gated
  items. Design item C7 (583f552f0, Nov 12: "headings and the help line count what the rows show") moved the heading and
  missed the tab. The World window's chip counts raw too (ZeD_WorldWindow.lua:5609; with a gate mod such as Immersive
  Searching it would give away the count the gate hides).
- Fix: liveCount(inv, playerObj) beside shownCount (InventoryRenderer.lua:2345) with buildItemModel's filter (not
  isHidden, not in heldSet for the player's own main inventory only, as isPlayerInv at :2144/:2150 with the heldByPlayer
  fallback at :2152, and ContainerGates.keeps), cached like ContainerGates.count (:101-110) on the item count, the worn
  count, both hands and the gate's sig; it must not depend on the list drawing, which stops while the side is rolled
  (:5215, :5276-5278). Use it in both windows' chips. Take the tab's name and the drop target from the same container:
  win._containers[win._viewedContainer or win._activeContainer] (a mouse pick of a bag on a non-Loot tab sets only
  _viewedContainer, :6252-6272, so today the tab can say Inventory over the bag's count while a drop goes into the bag).
