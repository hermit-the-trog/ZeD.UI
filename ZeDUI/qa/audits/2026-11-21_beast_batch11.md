# Beast day, batch 11 (Nov 21 2026, QA): what proving batch 10 turned up

Batch 10 is proven in game at 4K and 1280x800 on 2cff8f8f3 (vx10.txt: vx10_craft 24, vx10_food 24, vx10_tab 15,
vx10_defaults 17, all PASS; reports 2026-11-21_vx10b_4k.md and 2026-11-21_vx10_deck.md), and the release test is 15/15
at both sizes on it. These four came out of that work: B11-1 from the game itself (vx10_craft's information lines for
Build), B11-2 to B11-4 from the proof scripts' reviewers, each traced by one agent and attacked by a second (workflow
wf_0160e187-724; neither refuted).

### B11-1 The Craft card's Outputs name the wrong food and pot (B10-2's name half, seen in game)

- What the player meets: Divide Food into 4 Bowls with a pot of soup in reach: the Outputs read "Bowl of Pasta" 4 and
  "Cooking Pot" 1, while the game makes Bowl of Soup (Base.SoupBowl) and gives back the Cooking Pot. With a saucepan of
  rice (Base.RicePan): "Bowl of Pasta" and "Cooking Pot", while the game makes Bowl of Rice (Base.RiceBowl) and gives
  back the Saucepan. Proof: 2026-11-21_vx10b_4k.md, "ZEDQA vx10_crf info for Build (B10-2, the names)".
- Cause: CC.getOutputName (CraftingCore.lua:98-105) takes getPossibleResultItems():get(0), the mapper's first entry,
  whatever is in reach; vanilla's window (manual select, ISHandCraftPanel.lua:355) names the mapper's result for the
  items in the slots (ISWidgetOutput.lua:286-295).
- Fix: for an output with a mapper (output:getOutputMapper()), name the result for what the card's slots hold (or what
  is in reach), as vanilla does; the first result only when nothing fits. Note ObjectCardPreview.lua:181-215's
  carried-item pick never runs (getPossibleResultItems already returns the mapper's results, so its #types == 0 gate
  never opens): the same fix belongs there.

### B11-2 With "See Not Known Recipes" on (the game's default), must-learn recipe rows blink and the Craft list re-sorts every 1.2 s

- What the player meets: on the Craft tab every must-learn recipe he has not learned (and has the skill for) blinks
  between a gold square and a red square with a dimmed name about every 1.2 s, under Show: All and Known, and under
  Ready whenever a search or the open card lists one. The whole list is refiltered and re-sorted about every 1.2 s with
  nothing changing (a frame cost under every Show mode). Show: Known lists them and Sort: Known ranks them as known; a
  re-sort the player causes can catch them gold and lift the block above every missing row until the next scan drops
  it. Now and then the quick scan paints one green (Craft stays disabled: the game refuses it). The QA save prints
  SeeNotLearntRecipe true; all four sandbox presets set it true.
- Cause: CraftingTab.lua:278 calls isRecipeKnown(recipe), which is isRecipeKnown(recipe, false): with the option on it
  returns true at once (IsoGameCharacter bytecode, offsets 0-24). The game's own scan (CachedRecipeInfo.isValid via
  CraftRecipeManager.isValidRecipeForCharacter, offsets 73-79) asks isRecipeKnown(recipe, true) and says invalid. So the
  scan sets the row locked (CraftingCore.lua:522; the :526 guard does not fire, rd.learned is true), the next 1 s row
  refresh writes unlocked again (:578-580, :586), and a refresh always lands between two 1.2 s scans (CraftingTab.lua:182,
  :234; CraftingCore.lua:407), so every scan returns changed (:528) and sets filterDirty (CraftingTab.lua:579-581).
- Fix: CraftingTab.lua:278 pcall(playerObj.isRecipeKnown, playerObj, entry.recipe, true) (isRecipeActuallyKnown is the
  same call; RecipeIndex.lua:139 uses it). The same misread: JournalTab.lua:787 (the Journal counts every must-learn
  recipe as learned, so a recipe that is only unlearned never shows HOW TO LEARN and its magazine hint, CraftingCore.lua
  2813, 3006-3008; its rows read gold and undimmed) and RecipeIndex.lua:164 (also the item card's Known badge,
  ItemCardOrganism.lua:1333-1334). The Build tab has the same flicker from another cause: BuildingTab.lua:248-249
  hardcodes learned = true ("building recipes don't need to be learned"), but 32 vanilla build entities have
  NeedToBeLearn = true (entity_metal_* and entity_welding_*; Metal floor needs no skill at all), the BuildLogic scan
  (:416-417) marks them invalid, so the Build tab re-sorts every scan for anyone who has not learned Metal floor,
  whatever the setting: learned = isRecipeKnown(recipe, true) there too (it returns true when no learning is needed).

### B11-3 The World window's tucked-away tab names and drops into the wrong container (B10-5's second half)

- What the player meets: inventory pair open by a crate, the World list on Ground. Press Maps (or Craft, Build,
  Forage), click the crate's button on the World strip: the list, heading and title switch to the crate. Leave the
  pointer on the map 2 s: the side rolls up and its tab reads "Ground  N" with the ground's count, the help line says
  "Ground, N items" and pressing it rolls down the crate's list. A quick drop on the tab goes to the floor, not the
  crate the list showed. The mirror: with a crate the active container (clicked in the world), viewing Ground on Maps
  leaves the tab naming and counting the crate, and a quick drop goes into the crate. A controller pick never splits
  them. QA's vx10_tab part C rolled the World side with nothing picked, so it passed.
- Cause: 2cff8f8f3 moved the Character window's chip and dropInv to win._containers[win._viewedContainer or
  win._activeContainer] (ZeD_CharacterWindow.lua:6946-6957); in the World window it changed only the count
  (ZeD_WorldWindow.lua:5609-5610): the chip's name (:5607) and dropInv (:5613) still index _activeContainer, while a
  mouse pick on a non-Loot tab sets only _viewedContainer (:4040, :4050) and the list draws the view (:5012).
- Fix: index win._containers[win._viewedContainer or win._activeContainer] at :5607 and :5613. Ship with it one line in
  dropInv before its return: if e and not e.isFloor and not ZeD_WorldWindow.inReach(e.inventory, win.playerNum) then
  return nil end (inReach :3563-3570): the rolled list is frozen and vanilla's transfer action has no distance check,
  so with the index fix a quick drop on a tab naming a crate he walked away from would fill it from afar (the title-bar
  drop already refuses this, InventoryRenderer.lua:3707). QA adds the World twin of vx10_tab part B.

### B11-4 (small) The B10-4 hold can land 1 px short, and rarely creeps

- What the player meets: usually nothing; about 3 to 4% of the time the open recipe's row drops 1 px once at the next
  scan; very rarely (some list lengths) it creeps down 1 px per re-sort for minutes (worst seen 171 and 210 px). Most
  re-sorts come from B11-2's flicker, so B11-2's fix removes most of the exposure.
- Cause: the hold stores scrollPos = want / span (CraftingCore.lua:2247) and the list draws floor(scrollPos * span)
  (:2257); in doubles that can come back one ulp under the whole number.
- Fix: scroll:setScrollPos((want + 0.5) / span) at :2247 (clamped to 1.0 at Molecules.lua:1077); the controller follow
  at :3364 (newOff / span) can take the same change.
