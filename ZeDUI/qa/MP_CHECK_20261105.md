# Multiplayer check and benchmark (Nov 5 2026, QA)

The first time ZeD ran in multiplayer: a dedicated server on this machine (the one that ships with the game, no Steam,
its own folder `Zomboid/zedqa_mp`), the game joining it as the server's admin, 4K fullscreen at 1.75x, game 42.22.
Then a frame-rate and lag-spike benchmark, solo and on the server, with ZeD and with the game's own windows.

Tools (new): `tools/qa/mp_server.ps1` (-Start / -Stop, -Mods ZeD_UI or ZeDQAShim), `zedqa_run.ps1 -Mp` (joins the
server from the main menu), `mp_smoke.lua`, `mp_actions.lua`, `mp_hand_after.lua`, `perf_motion.lua`. Reports in
`qa/regression/2026-11-05_*`. A code read of all of ZeD's Lua for multiplayer hazards (a helper, read only) came first.

## What works

- The server loads ZeD with no errors. ZeD's shared files run there too (the font scaler installs itself on the
  server), which costs a little server work but breaks nothing.
- Joining works. ZeD's own Spawn Location, Occupation and Character screens draw and work in multiplayer.
- In game: both windows open on Loot, the belt, the help line and the hint strip draw. No ZeD errors in the client log.
- From the code read, and not contradicted in game: item moves, cars, ovens, generators, campfires, washers, farming,
  animals, map notes and the trash all go through the game's own networked actions. Sandbox in game is already blocked
  on a client; the pause menu's Mods page is read only.
- A ZeD timed action that exists only on the client (opening a card after walking) ran to its end on the server.

## What breaks

1. **Unequip on a hand item does not reach the server.** ZeD's Unequip on a tool or weapon in the Equipment tab empties
   the hand on your screen only. Checked: a hammer equipped the game's way, then ZeD's Unequip, then a rejoin: the
   hammer was back in the main hand. Other players keep seeing it in your hand too.
   `client/ZeD/EquipmentTab.lua:1066-1074`. Fix: queue the game's unequip action, as ZeD already does for clothing
   on the same line and in `HealthTab.lua:905`.
2. **The watch's Speed key speeds up your own clock.** Pause does nothing on a server (time keeps running, rightly),
   but Fast Forward raised the client's time multiplier: the clock on your screen ran about ten times fast while the
   server's did not. Whether the server pulls it back, and how fast, was not measured. `client/ZeD/ZeD_Watch.lua:284-305`
   and `:637`. Fix: on a server, the watch's Start and Speed do nothing and say "server time", as the ZeD wheel
   already does (`ZeD_DpadWheels.lua:1158`).
3. **The game's speed buttons still show** at the top right on a server (ZeD hides them solo, then shows them back),
   and they do nothing there. Cosmetic.

## Not tested in game (from the code read, worth a look)

- **Cooking's Make** (the Cooking tab adds ingredients one after another) keeps the dish between adds in a table on
  your client, filled in when each add finishes. If 42.22 finishes the add on the server, every ingredient after the
  first would go into a fresh pot. `CookingTab.lua:338-363`. Needs a cook on the server.
- **Radio keys** (power, channel, volume, presets in the Radio tab, the car radio and the dashboard) change the set
  directly instead of queuing the game's radio action. The setting itself goes through the game, so it probably
  shows for others; what is skipped is the reach check and the click others hear. `RadioTab.lua:1446-1481`,
  `ZeD_RadioOps.lua:241-254`.
- **Dashboard ash tray and taxi meter** live on your client only: other passengers see their own. Display only.
- "Save and quit" in the pause menu disconnects on a server (it cannot save there). Wording only.

## Frame rate and lag spikes

Same walk for every run: the Valley Station mall, a 24-square aisle with 28 containers along it, there and back with
the game's own walk, so the World window refreshes its containers as you pass. Per scene 20 s standing or 30 s walking,
two passes. "Spikes" are frames over 33 ms (a dropped frame at 30 fps).

**Solo** (no server running; the frame cap is 120):

| Scene | ZeD fps | Game's own fps | ZeD worst frame | Game's worst frame | ZeD spikes | Game's spikes |
|---|---|---|---|---|---|---|
| Windows shut, standing | 119.4 | 120.0 | 37-38 ms | 13-15 ms | 2-5 | 0 |
| Windows open, standing | 117-119 | 120.0 | 32-43 ms | 17-19 ms | 0-5 | 0 |
| Windows shut, walking | 117-119 | 118-119 | 37-41 ms | 23-78 ms | 3-6 | 0-1 |
| Windows open, walking | 118.5 | 118.5 | 35-37 ms | 22-23 ms | 3 | 0 |

- **Frame rate: ZeD now holds the cap with both windows open.** On Oct 22 the same kind of scene ran at 76 fps against
  the game's 120; the belt, list and Skills work since then closed that gap.
- **Lag spikes: ZeD has a few the game's windows do not.** About one frame every 5 to 10 seconds takes 35 to 43 ms,
  windows open or shut, standing or walking. A player at 120 fps may feel these as a tiny stutter. The game's own
  windows have none standing (one 78 ms hitch while walking, from the world, not the UI). The cause is not found yet:
  the steady draws were measured on Oct 29; something periodic (a refresh on a timer, a rebuild every few seconds, or
  garbage collection after many small tables) is the next thing to profile.

**On the server** (server and game on the same machine):

| Scene | ZeD fps | Game's own fps | ZeD spikes over 50 ms | Game's spikes over 50 ms |
|---|---|---|---|---|
| Windows shut, standing | 40-47 | 29-30 | 2-4 | 0-2 |
| Windows open, standing | 38-40 | 29-30 | 2-4 | 0-1 |
| Windows shut, walking | 36-41 | 29-30 | 5-9 (one 146 ms) | 4 |
| Windows open, walking | 40 | 28-30 | 2-4 | 1-8 (one 170 ms) |

- Both are far below solo, and the game's own windows sat at a flat 30 fps (33 ms frames): the server shares this
  machine's processor, and the vanilla run looks capped by something other than the UI. These numbers say only that
  ZeD does not make a client slower on a server than the game's own windows do; they are not a fair head-to-head.
  A fair one needs the server on another machine.

## Options for the director

- Unequip and the watch speed (1, 2) are small, clear fixes for Build in Beta 4.
- Cooking on a server (not tested) should get one cook through before players find it.
- The lag spikes need a profile pass of their own (QA can run it next).
- The multiplayer surfaces you asked for (a Server tab, Admin, chat on the belt, PvP) are design work; the speed
  buttons (3) go away naturally once the watch knows it is on a server.

## Notes

- The QA character died once on the server: the benchmark gave back its protection at the end while it stood in the
  mall. The script now keeps the test character protected on the server.
- Not tested: more than one player, a server on another machine, Steam joining, PvP, safehouses, factions.
